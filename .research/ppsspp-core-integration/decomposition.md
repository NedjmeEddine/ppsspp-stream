# Problem Decomposition: PPSSPP WebAssembly Core Integration

> **Fast Recon Snapshot:** Local toolchain is Emscripten `emcc 7.0.0` (`~/.local/share/emsdk`), Go `1.27.4` (`go.mod` `1.22`), Node `v26.13.1`, Playwright `^1.65.1`, and `externals/vfs-streamer` pinned at `a3b8bd63d76014cfaab8224c38c32326e9188e44`. Existing scaffold already provides `VfsBlockDevice` (2048 B sectors), ISO9660/`UMD_DATA.BIN` identification, HTTP 206 `ppsspp-server`, OPFS-partitioned `worker_b.js`, and memory HUD.

## Kill Criteria
- **Target Runtime & Browsers:** Desktop Chromium and Firefox with `SharedArrayBuffer` (COOP `same-origin`, COEP `require-corp`), `WebGL2`, `WebAudio`, `Gamepad API`, and `OPFS` (`createSyncAccessHandle` with 4x `NoModificationAllowedError` retry). Safari/WebKit and mobile touch controls are out of scope for V1.
- **Local Toolchain & Build Reproducibility:** Must compile reproducibly on Linux `x86_64` using the repo's local `emsdk` (`emcc 7.0.0`) with pinned upstream commit SHA, build flags, and C ABI documented in `docs/CORE_PORT.md` (zero opaque `.wasm` binaries).
- **Submodule & Separation Boundaries:** `externals/vfs-streamer` MUST remain unmodified at upstream commit `a3b8bd6+` with zero build artifacts written inside it.
- **License Policy:** Upstream PPSSPP core source/binary may be GPLv2+; all `ppsspp-stream` Go server, JS shell, and `VfsBlockDevice` glue stay cleanly separated from upstream PPSSPP sources.
- **VFS & Memory Safety Invariants:** Configurable `16–64 MB` `SharedArrayBuffer` VFS cache slab (`RETRY_SMALLER_POOL` fallback down to `16 MB`). `VfsBlockDevice::Read` enforces strict EOF (`false`, never clamped), `<= 64 MiB` `wasm32` slicing, and zero per-read heap allocations. Struct sizes queried via `_vfs_client_ctx_size()` / `_vfs_fs_struct_size()`; `SharedArrayBuffer` views `.slice()`d before `TextDecoder.decode()`.
- **Performance & Format Bounds:** Raw ISO9660 `.iso` only in V1; cold local boot `< 2s`, warm OPFS reload `< 500ms`, sustained `>= 30 FPS` over a 5-second warm window, VFS `totalStallNs < 10%` of emulation wall time once warm.
- **OPFS Isolation & Teardown Safety:** Partition OPFS per `gameId` (`cache_${gameId}.opfs`, `/saves/${gameId}/`); `BuildEtagHash` cache invalidation never deletes `/saves/${gameId}/`; deterministic `AudioContext.close()` and `TELEM_FLUSHED` ack (bounded timeout) before Worker B termination; zero stuck inputs on `window.blur`.

## Sub-Problem Axes
- wasm-memory-topology | HARD_TO_REVERSE | Should PPSSPP and the VFS client link into a single shared-memory WASM module (Option A zero-copy) or stay decoupled as two WASM modules bridged via a bounce buffer (Option B) given 32-bit WASM address space, pthreads, Emscripten memory growth, and rebase cost?
- ppsspp-emscripten-build | HARD_TO_REVERSE | Which upstream PPSSPP revision or active Emscripten port and build configuration (pthreads, HLE CPU IR interpreter vs JIT, GLES3/WebGL2, headless/libretro vs SDL frontend, BlockDevice injection seam) compiles reproducibly on Emscripten 7.0.0 without maintaining fragile forks?
- webgl2-canvas-threading | HARD_TO_REVERSE | Should PPSSPP own a WebGL2 OffscreenCanvas directly inside Worker A (Emscripten pthread) or proxy WebGL2 commands through the main thread across desktop Chromium and Firefox without pthread deadlocks, resize bugs, or broken teardown on game switch?
- audio-streaming-backend | MODERATE | Which low-latency stereo 44.1/48 kHz PCM transport from the emulation worker to WebAudio (Emscripten Wasm Audio Worklets, custom AudioWorklet + SAB SPSC ring buffer, or main-thread scheduled buffers) prevents underruns while guaranteeing deterministic AudioContext.close() teardown?
- memstick-opfs-bridge | MODERATE | How should PPSSPP's virtual Memory Stick (/PSP/SAVEDATA POSIX file I/O) synchronize with Worker B's partitioned OPFS /saves/${gameId}/ directory without blocking emulation frames or losing dirty writes on exit, game switch, or tab close?
